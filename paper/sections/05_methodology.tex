\section{Methodology}
\label{sec:method}

\subsection{Trace and split}
Our main dataset is the job log of the Microsoft Philly trace~\cite{jeon19}. Jobs are split by submission time (UTC): training before 1~November 2017, validation from 1 to 14~November, and test from 15~November to 15~December. The predictors are trained and tuned on the first two periods only.
The simulation starts on 8~November, so the seven days before the test window are a warm-up that fills the queue and the pool. It replays \MethSimJobs{} jobs: \MotTestJobs{} test jobs, \MethWarmupJobs{} warm-up jobs and \MethCarryJobs{} carry-over jobs. Jobs already running on 8~November enter at time zero with their elapsed time (\MethCarryJobs{} carry-over jobs on \MethCarryGpus{} GPUs).
Baseline statistics count only the \MotTestJobs{} test jobs. The cost of a policy is the paired difference over all jobs.

\subsection{Pool and baseline check}
The trace has \SetupInstalledGpus{} installed GPUs, of which about \SetupPoolGpus{} report a utilisation value in a typical test-window minute; we simulate a pool of \SetupPoolGpus{} GPUs.
Table~\ref{tab:baseline} compares the simulated baseline with the trace. Busy GPUs and utilisation match, whereas waits do not, because the simulator has no virtual-cluster quotas, placement constraints or start-up delay. The simulator was not tuned to match the waits.

\subsection{Grid events}
An event lasts 1, 2 or 4~hours and asks for a cut of 10, 20 or 30\%. All nine combinations share the same \MethEventDays{} start times. A fixed seed draws \MethEventDays{} distinct days between \MethEventFirstDate{} and \MethEventLastDate{}, and one half-hour slot per day from \MethEventFirstStartHhmm{} to \MethEventLastStartHhmm{} Pacific time.
This gives \SetupEventsTotal{} events. In \SetupEventsInfeasible{} of them, all with a \SetupInfeasibleCutPct\% cut, the target is below the idle floor $P_{\text{floor}}$. We exclude them, which leaves \SetupEventsFeasible{} events. The default cell is 2~hours and 20\%.
Each event is a paired run: the baseline and every policy start from the same snapshot at $t_s$ and run until 24~hours after the event ends.

\subsection{Second trace: Acme}
We also use the job log of AcmeTrace~\cite{hu24} from Seren, a cluster of \AcmePoolGpus{} A100 GPUs used to develop large language models; its second cluster, Kalos, runs a mean of only \AcmeMotKalosEveningRunningJobsMean{} jobs at 17:00--20:00, so we exclude it. The split uses China time (UTC+8): training before 15~June 2023, validation to 28~June, test from 29~June to 29~July. The simulation starts on 22~June and replays \AcmeMotSimJobs{} jobs (\AcmeMotTestJobs{} test, \AcmeMotWarmupJobs{} warm-up and \AcmeMotCarryJobs{} carry-over jobs). Events start from 17:00 to 19:30 China time on \MethEventDays{} days, with the same durations and cuts as on Philly; none is infeasible.
The maximum GPU power is that of the A100\footnote{\raggedright NVIDIA A100 Tensor Core GPU datasheet, \url{https://www.nvidia.com/content/dam/en-zz/Solutions/Data-Center/a100/pdf/nvidia-a100-datasheet-us-nvidia-1758950-r4-web.pdf}, accessed 19 November 2026.}; the idle and host power come from the measured GPU and server power of the trace~\cite{hu24}. Without per-job utilisation, all jobs share one value, chosen so that the simulated mean GPU power over the test window (\AcmeSimGpuPowerW\,W) matches the measured mean (\AcmeCdfGpuPowerW\,W, from August 2023). The cloud price is the on-demand price of an eight-A100 instance per GPU\footnote{\raggedright AWS EC2 p4d.24xlarge (eight A100), on-demand, us-east-1, as listed at \url{https://instances.vantage.sh/aws/ec2/p4d.24xlarge}, accessed 19 November 2026.}; \$\AcmeHighPrice{} is a sensitivity check. Cancelled and preempted jobs count as useful work (we assume their checkpoints are kept), so only failed, node-failure and time-out jobs are waste, and the controller uses $q_j=1-p^{\text{fail}}_j$. The learned predictors also use the job type of the trace, a label set at submission; a LightGBM without it has the same pinball loss (\AcmePredLightgbmNotypePinball{} against \AcmePredLightgbmPinball{}).
The baseline matches the trace in busy GPUs (\AcmeSimBusyGpusMean{} simulated, \AcmeRealBusyGpusMean{} real) and utilisation (\AcmeSimUtilisationMean{} and \AcmeRealUtilisationMean{}); as on Philly, the simulated waits are shorter.

\subsection{Predictors and policies}
We compare five predictors (Section~\ref{sec:design}): the last-two-jobs average~\cite{tsafrir07}, gradient-boosted trees, LightGBM~\cite{ke17}, the transformer, and the oracle. Each writes rows on the elapsed-time grid.
\MethNoPredJobs{} simulated jobs, \MethNoPredCarryJobs{} of them carry-over jobs, have no prediction row and use their true values. The \MethCensoredJobs{} jobs with no observed end run until the end of the log, a lower bound on their runtime, and count as Pass. Because these jobs run long, they hold a median of \MethNoPredGpuShareMedianPct\% of the running GPUs at an event start; Section~\ref{sec:eval} shows that this fallback does not change the results.
The policies are delay-only, cap-only, burst-only, the mix with the median or the 90th-percentile cloud bill, and mix-nocloud: the same mix with no cloud capacity ($C_{\max}=0$), which isolates the effect of bursting from that of capping and job choice.

\subsection{Parameters and metrics}
Table~\ref{tab:params} lists the main parameters. The maximum GPU power is that of the P100\footnote{\raggedright NVIDIA Tesla P100 PCIe datasheet, \url{https://nvidia.com/content/dam/en-zz/Solutions/Data-Center/tesla-p100/pdf/nvidia-tesla-p100-PCIe-datasheet.pdf}, accessed 13 November 2026. The trace names no GPU model. The cloud instance below has a V100 GPU; cloud power is used only for the carbon check.}, the PUE is the industry average of a survey\footnote{\raggedright Uptime Institute Global Data Center Survey 2023, \url{https://journal.uptimeinstitute.com/large-data-centers-are-mostly-more-efficient-analysis-confirms/}, accessed 13 November 2026.}, and the cloud price is the on-demand price of a one-GPU instance\footnote{\raggedright AWS EC2 p3.2xlarge (one V100), on-demand, us-east-1, as listed at \url{https://instances.vantage.sh/aws/ec2/p3.2xlarge}, accessed 13 November 2026.}.
For each event and policy we compute the cost in dollars per MWh shed (Eq.~\ref{eq:usdmwh}). A policy can win a cell only if its compliance is at least 99\%. To compare policies we divide each policy's cost by the delay-only cost of the same event and report the median of this ratio over events. All runs use one seed.
